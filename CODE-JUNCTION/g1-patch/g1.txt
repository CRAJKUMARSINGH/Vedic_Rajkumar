```ts
export const AYANAMSA_ENGINE_VERSION = '2.0.0' as const;
export const J2000 = 2451545.0;

export type AyanamsaSystem = 'Lahiri'|'Raman'|'KP'|'Yukteshwar'|'FaganBradley'|'TrueCitra';
export type AyanamsaSource = 'swisseph' | 'precession-polynomial';
export type AnchorProvenance = 'golden-locked' | 'pending-golden';
export type AyanamsaDegraded =
  | 'true-citra-approximated' | 'anchor-pending-golden' | 'delta-t-out-of-range';

export const AYANAMSA_ANCHORS: Readonly<Record<AyanamsaSystem, AyanamsaAnchor>> = {
  Lahiri:        { seSidMode: 1,  valueAtJ2000: 23.853194, provenance: 'golden-locked',  trueStar: false, ... },
  Raman:         { seSidMode: 3,  valueAtJ2000: 22.45986,  provenance: 'pending-golden', trueStar: false, ... },
  KP:            { seSidMode: 5,  valueAtJ2000: 23.85022,  provenance: 'pending-golden', trueStar: false, ... },
  Yukteshwar:    { seSidMode: 7,  valueAtJ2000: 22.36,     provenance: 'pending-golden', trueStar: false, ... },
  FaganBradley:  { seSidMode: 0,  valueAtJ2000: 24.74261,  provenance: 'pending-golden', trueStar: false, ... },
  TrueCitra:     { seSidMode: 27, valueAtJ2000: 23.853194, provenance: 'pending-golden', trueStar: true,  ... },
};

/** IAU 2006 accumulated general precession in longitude, arcsec (Capitaine et al. 2003). */
export function precessionArcsec(jdTT: number): number {
  const T = (jdTT - J2000) / 36525;
  return 5028.796195*T + 1.1054348*T**2 + 0.00007964*T**3 - 0.000023857*T**4 - 0.0000000383*T**5;
}

export function ayanamsaAt(jdUT: number, system: AyanamsaSystem = 'Lahiri'): AyanamsaValue {
  if (!isFiniteNumber(jdUT) || jdUT <= 0) throw new RangeError('ayanamsaAt: jdUT must be positive');
  const anchor = AYANAMSA_ANCHORS[system];
  if (!anchor) throw new RangeError(`ayanamsaAt: unknown ayanamsa system "${String(system)}"`);

  const { jdTT, inRange } = jdTTFromUT(jdUT);
  const degraded: AyanamsaDegraded[] = [];
  let value = anchor.valueAtJ2000 + precessionArcsec(jdTT) / 3600;

  if (anchor.trueStar) { value += nutationInLongitudeArcsec(jdTT)/3600; degraded.push('true-citra-approximated'); }
  if (anchor.provenance !== 'golden-locked') degraded.push('anchor-pending-golden');
  if (!inRange) degraded.push('delta-t-out-of-range');

  return { system, jdUT, jdTT, value: normalise(value),
    precessionRate: precessionRateArcsecPerCentury(jdTT)/3600,
    source: 'precession-polynomial', seSidMode: anchor.seSidMode,
    engineVersion: AYANAMSA_ENGINE_VERSION, degraded };
}
```

It also exports `deltaTSeconds()` (Espenak–Meeus, valid 1900–2150, out-of-range flagged rather than extrapolated), `nutationInLongitudeArcsec()` (IAU 1980 leading terms), `boundaryMargins()` and `systemsDisagreeAcrossBoundary()` for Phase 2.

## 2 · Phase 2 patch plan

**Download: [PHASE2_CODE_PATCH_PLAN.md](https://www.genspark.ai/api/files/s/xxrlp3Qt)**

Three workstreams, 11 files. The core of it:

**WS-1 — router fail-rules.** `src/api/v1/router.ts:127` ships `getNatal() { return { lagnaSign: 0, planets: { Moon: 45 } } }`, and `/v1/transits/:chartId` returns **HTTP 200** from it. New `src/api/v1/errors.ts` defines `ApiErrorCode` (`chart_not_computed`, `compute_unavailable`, `ephemeris_degraded`, `anchor_pending_golden`, …) and `serviceUnavailable()` → 503 with a machine `reason`. Route table: charts POST → 503 `compute_unavailable`; charts GET → 404 or 503; transits → 503 `chart_not_computed`; answer → 404 for an unknown person, never a 200 card about nobody.

**WS-2 — confidence caps.** `confidence.ts` starts at 0.55, adds, then clamps to `[0.2, 0.9]` — with **no cap tied to a degraded input**, and its caveat detection is a regex on prose (`/not SAV-certified/`) that any copy edit silently disables. Replaced with a cap table applied *after* the additive score:

| # | Condition | Cap |
|---|---|---|
| C1 | any position `source: 'mean-motion'` | 0.40 |
| C2 | `true-citra-approximated` | 0.55 |
| C3 | `anchor-pending-golden` | 0.60 |
| C4 | `delta-t-out-of-range` | 0.65 |
| C5 | Lahiri vs Fagan-Bradley disagree on the nakshatra | 0.50 |
| C6 / C7 | boundary margin < 0.05° / < 0.25° | 0.55 / 0.68 |
| C8 / C9 / C10 | SAV / Ashtakavarga / Moon-transit flags false | 0.72 / 0.75 / 0.80 |
| C11 | ≥3 unresolved conflicts | 0.62 |
| — | none | 0.90 |

With a 0.60 cap a card can never read "high" (≥0.75). That is the point.

**WS-3 — answer-card source tagging.** `provenance.ephemeris` is `'local' | 'swisseph'` — it cannot express the endpoint engine, the polynomial path, or mean motion — and `ayanamsa: string` never records *which system* produced the number. Widen to a 4-value union, add `ayanamsa_system` / `ayanamsa_source` / `ayanamsa_value` / `ayanamsa_degraded` / `position_sources`, bump `ANSWER_CONTRACT_VERSION` to **1.3**. Then `assertProvenancePublishable()` in `publishGuard.ts` makes it enforceable: a card with a `pending-golden` anchor or a mean-motion position **throws instead of publishing**.

## 4 · Deep research — ayanamsa regression-test strategy

**Download: [AYANAMSA_REGRESSION_RESEARCH.md](https://www.genspark.ai/api/files/s/YltH9Zse)**

The finding that reorganises the problem: **ayanamsa accuracy cannot be validated by an ephemeris.** An ephemeris gives tropical positions. The ayanamsa is a *definition* — Lahiri is not a number Swiss Ephemeris knows, it is the construction placing Spica (Chitra) at exactly 180° of sidereal longitude at an epoch-anchored frame. So testing SE-derived golden values against SE proves nothing — and your repo currently escapes circularity only by accident: `scripts/accuracy-golden.mjs` generates golden values from `swisseph-wasm` while production runs the local polynomial. **The moment production moves to `swisseph-wasm`, that test becomes circular.**

### Engine comparison

| Engine | Method | Planets | Moon | Range | Licence | Fit |
|---|---|---|---|---|---|---|
| **Swiss Ephemeris** (`swisseph-wasm`) | Chebyshev from JPL DE + own ayanamsa implementations; Moshier fileless mode | reproduces parent JPL to ~**0.001″**; one open benchmark reports **median 0.05″** vs Horizons; Moshier mode **~1″** | Moshier **~3″** | files 1800–2399; Moshier −3000…+3000 | **AGPL-3.0-or-later** / commercial ~CHF 700 | Already the ADR-007 decision — keep as **oracle** |
| **JPL DE440/DE441 via Skyfield** | Direct Chebyshev kernel | sub-arcsecond by construction | exact | DE440 **1550–2650**; DE441 **−13200…+17191** | Skyfield MIT, kernels free | **Best independent oracle** — different codebase, catches *implementation* bugs |
| **astropy builtin** (ERFA `epv00`/`plan94`) | Analytical, no download | arcsecond-class | limited | wide | BSD | Good for precession/obliquity; weak positional oracle |
| **astropy + DE430** | Chebyshev | sub-arcsecond | exact | **1550–2650** | BSD | Heavier Skyfield equivalent |
| **VSOP87** | Analytical series | **~1″** over ±2000 yr | **none** (needs ELP2000) | ±4000 yr | public domain-ish | Third opinion for planets; useless for the Moon — the body Jyotish actually cares about |
| **Moshier** | Analytical, in-memory | **0.1″–1″** (sources conflict) | **~3″** | −3000…+3000 | via SE (AGPL) | Viable for a WASM-less client, but 3″ on the Moon ≈ 0.0008° — fine for a rashi, marginal at a pada edge |

Read together, the bottleneck for this product is **not** planetary theory — every candidate is within a couple of arcseconds, and a pada is 1867″ wide. The bottleneck is the ayanamsa definition, time scales and time zones. Your own defects confirm it: F-01, F-02, F-03, F-06 are all anchor/time bugs.

### The one trap in the Lahiri definition

Lahiri anchors Spica at 180°00′, which is why it is called *Chitrapaksha*. But Spica's **actual** longitude today is nearer **29° Virgo than 0° Libra** — the ~1° gap between the epoch-anchored construction and a naive "Spica is at 180° right now" reading. A Tier-1 test that assumes Spica sits at 180° today would be wrong by ~1°, larger than every other error in the report combined.

### Recommended strategy: a four-tier ladder

| Tier | Proves | Oracle | Tolerance |
|---|---|---|---|
| **T0** | Invariants — ratios, monotonicity, derivative consistency | none, pure math | exact, <1 s |
| **T1** | The *definition* is implemented correctly | independent Spica astrometry from a star catalogue + precession | 1–2″ |
| **T2** | The *body pipeline* matches an authority | Swiss Ephemeris golden vectors | Tier A 1″ / Tier B 5″ |
| **T3** | The authority isn't drifting | JPL Horizons spot checks + Skyfield/DE440 | 1″ |

You have T0 (delivered), T2 (exists) and T3 (missing). **T1 is the missing tier, and the only one that would have caught the Fagan-Bradley `24.0440` typo and the dropped T² precession term.** Until it exists, the delivered `validateLahiriFormula()` is the cheap stand-in: it asserts *definitional relations* between systems (FB−Lahiri 0.85–0.93°, Raman−Lahiri 1.38–1.41°, |Lahiri−KP| < 0.02°, rate 49.9–50.6″/yr, monotonic 1900→2000→2026) which hold regardless of engine and fail loudly on a typo.

Harness verdict: **Vitest + committed golden JSON for T2**; **pytest-regressions as an offline generator for T1** whose output is a committed JSON that Vitest asserts against (generate in one language, assert in another — keeps CI in TS); **Skyfield + Horizons for T3, quarterly**; **fast-check property tests for T0**; **reject full-chart snapshots.** And a tolerance-increase guard: raising a tolerance requires a line in `docs/accuracy/METHODOLOGY.md` saying why, so "fix the test" isn't the reflex.

Residual uncertainty, stated plainly: the exact Lahiri anchor epoch *as SE implements it* is not stated in anything I retrieved (the "mean equinox 285" formulation is Lahiri's own description as quoted on the swisseph list, not SE's source comment); SE accuracy figures are vendor/practitioner claims and the Moshier figures conflict between sources; `swisseph-wasm`'s fidelity to the C library is untested by anything I found — a real gap belonging to Tier 3. I ran no candidate engine; the delivered Phase 1 patch is the only code compiled and executed here.
