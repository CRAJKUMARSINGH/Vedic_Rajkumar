# Requirements Document

## Introduction

Legal Luminaire's Omni-Modal Ingestion feature eliminates manual data entry for junior lawyers (nascent advocates) by allowing them to upload raw legal artifacts — smartphone photos of FIRs, scanned PDF contracts, handwritten panchnamas, and plain text — and have the system automatically read, structure, and instantiate a new digital case file. The system acts as a Virtual Senior Advocate, guiding junior lawyers through document classification, fact extraction, legal issue spotting, draft generation, and chamber review workflows.

## Glossary

- **System**: The Legal Luminaire Omni-Modal Ingestion backend and frontend application
- **Ingestion_Engine**: The subsystem responsible for receiving, storing, and routing uploaded files
- **PDF_Parser**: The subsystem that extracts text content from PDF documents
- **OCR_Engine**: The subsystem that performs Optical Character Recognition and Handwritten Text Recognition on image files
- **Classifier**: The AI subsystem that categorizes uploaded documents into legal document types
- **PII_Redactor**: The subsystem that detects and redacts personally identifiable information before LLM processing
- **Fact_Extractor**: The AI middleware that extracts structured legal facts from parsed document text
- **Timeline_Builder**: The subsystem that constructs a chronological event timeline from extracted dates and facts
- **Issue_Spotter**: The AI subsystem that cross-references IPC/BNS sections and identifies procedural defects
- **Explanation_Layer**: The tutorial subsystem that provides contextual legal explanations and Supreme Court precedent references
- **Review_UI**: The split-screen human-in-the-loop interface for reviewing and correcting AI-extracted content
- **Research_Engine**: The AI subsystem that fetches relevant legal precedents based on extracted case facts
- **Draft_Generator**: The subsystem that produces court-ready legal document drafts
- **Citation_Verifier**: The subsystem that validates all legal citations in generated drafts against known databases
- **Formatter**: The subsystem that applies court-specific and jurisdiction-specific formatting rules to drafts
- **Case_Dashboard**: The structured digital case file view instantiated after ingestion is complete
- **Chamber_Review**: The workflow by which a senior advocate reviews and approves a junior advocate's case file and drafts
- **Junior_Advocate**: A nascent lawyer user who uploads documents and initiates case creation
- **Senior_Advocate**: A supervising lawyer user who reviews and approves case files and drafts
- **FIR**: First Information Report — a police document initiating a criminal case
- **Panchnama**: An official witness document used in Indian criminal proceedings
- **IPC**: Indian Penal Code
- **BNS**: Bharatiya Nyaya Sanhita (successor to IPC)
- **PII**: Personally Identifiable Information (names, Aadhaar numbers, addresses, phone numbers)
- **HTR**: Handwritten Text Recognition
- **Case_Record**: The persistent PostgreSQL database record representing a single legal case

## Requirements

### Requirement 1: Persistent Case Storage

**User Story:** As a Junior_Advocate, I want new case files to be stored persistently in a database, so that I can access them across sessions and devices without losing data.

#### Acceptance Criteria

1. WHEN a Junior_Advocate creates a new case, THE System SHALL persist the Case_Record to a PostgreSQL database via Drizzle ORM.
2. THE System SHALL expose a REST API endpoint to create a new Case_Record with fields: case title, case type, jurisdiction, date created, and assigned advocate ID.
3. THE System SHALL expose a REST API endpoint to retrieve a Case_Record by its unique identifier.
4. IF a database write operation fails, THEN THE System SHALL return an HTTP 500 response with a descriptive error message and SHALL NOT create a partial Case_Record.
5. THE System SHALL store all uploaded raw files in object storage (AWS S3 or Cloudflare R2) and record the storage URL in the Case_Record.

---

### Requirement 2: PDF Parsing

**User Story:** As a Junior_Advocate, I want to upload PDF documents of any length, so that the system can extract their full text content for analysis.

#### Acceptance Criteria

1. WHEN a PDF file is uploaded, THE PDF_Parser SHALL extract the full text content from all pages of the document.
2. THE PDF_Parser SHALL support PDF documents up to 500 pages in length.
3. WHEN a PDF document exceeds 50 pages, THE PDF_Parser SHALL split the document into chunks of at most 50 pages each before processing.
4. IF a PDF file is password-protected or corrupted, THEN THE PDF_Parser SHALL return a descriptive error message identifying the file by name.
5. WHEN PDF parsing is complete, THE PDF_Parser SHALL emit a structured output containing the extracted text, page count, and chunk boundaries.

---

### Requirement 3: Image OCR and Handwritten Text Recognition

**User Story:** As a Junior_Advocate, I want to upload smartphone photos and scanned images of legal documents, so that the system can extract text including handwritten notes.

#### Acceptance Criteria

1. WHEN an image file (JPEG, PNG, TIFF, or WEBP) is uploaded, THE OCR_Engine SHALL extract all printed text from the image.
2. WHEN an image contains handwritten text, THE OCR_Engine SHALL apply HTR to extract the handwritten content alongside printed text.
3. THE OCR_Engine SHALL support documents written in English, Hindi, and Gujarati scripts.
4. WHEN OCR processing is complete, THE OCR_Engine SHALL emit a structured output containing the extracted text, detected language, and a confidence score between 0.0 and 1.0.
5. IF the OCR_Engine produces a confidence score below 0.6 for any page, THEN THE System SHALL flag that page for manual review by the Junior_Advocate.

---

### Requirement 4: Omni-Modal Upload Interface

**User Story:** As a Junior_Advocate, I want a single upload interface that accepts PDFs, images, and text files simultaneously, so that I can submit all case artifacts in one step.

#### Acceptance Criteria

1. THE System SHALL provide a drag-and-drop upload zone that accepts PDF, JPEG, PNG, TIFF, WEBP, and plain text (.txt) file types simultaneously.
2. WHEN a file is added to the upload zone, THE System SHALL display a thumbnail preview and the file name within 1 second.
3. WHILE a file is being uploaded and processed, THE System SHALL display a live progress indicator showing the current processing stage (uploading, parsing, OCR, classifying).
4. THE System SHALL support uploading a minimum of 20 files in a single case creation session.
5. IF a file exceeds 100 MB in size, THEN THE System SHALL reject the file and display an error message stating the size limit before upload begins.
6. IF an unsupported file type is dropped onto the upload zone, THEN THE System SHALL display an error message listing the supported file types.

---

### Requirement 5: Document Classification

**User Story:** As a Junior_Advocate, I want uploaded documents to be automatically categorized by type, so that I do not have to manually label each artifact.

#### Acceptance Criteria

1. WHEN extracted text from a document is available, THE Classifier SHALL assign the document one of the following types: FIR, Bail_Order, NDPS_Seizure_Memo, Civil_Contract, Charge_Sheet, Court_Order, or Unknown.
2. THE Classifier SHALL produce a classification confidence score between 0.0 and 1.0 for each assigned type.
3. IF the Classifier assigns a confidence score below 0.75, THEN THE System SHALL present the classification to the Junior_Advocate for manual confirmation before proceeding.
4. WHEN a document is classified, THE System SHALL store the document type and confidence score in the Case_Record.

---

### Requirement 6: PII Redaction

**User Story:** As a Junior_Advocate, I want personally identifiable information to be automatically redacted before any document text is sent to an LLM, so that client confidentiality is protected.

#### Acceptance Criteria

1. WHEN document text is prepared for LLM processing, THE PII_Redactor SHALL detect and redact the following entity types: full names, Aadhaar numbers, phone numbers, email addresses, and physical addresses.
2. THE PII_Redactor SHALL replace each detected PII entity with a typed placeholder (e.g., [NAME], [AADHAAR], [PHONE]).
3. THE System SHALL maintain a secure mapping between placeholders and original PII values, stored encrypted in the database, accessible only to authenticated advocates assigned to the case.
4. THE PII_Redactor SHALL process document text before it is transmitted to any external LLM API endpoint.
5. IF the PII_Redactor fails to complete redaction for any document chunk, THEN THE System SHALL halt LLM processing for that chunk and log the failure.

---

### Requirement 7: Fact Extraction and Case Field Population

**User Story:** As a Junior_Advocate, I want the system to automatically populate structured case fields from uploaded documents, so that I do not have to manually transcribe information.

#### Acceptance Criteria

1. WHEN redacted document text is available, THE Fact_Extractor SHALL identify and extract values for the following fields: Incident_Type, Evidence_Type, Jurisdiction, Accused_Count, Complainant_Type, and Applicable_Sections.
2. THE Fact_Extractor SHALL populate the corresponding fields in the Case_Record with the extracted values.
3. WHEN the Fact_Extractor identifies a date or time reference in the document text, THE Timeline_Builder SHALL add a timestamped event entry to the case timeline.
4. THE Timeline_Builder SHALL sort all timeline entries in ascending chronological order.
5. IF the Fact_Extractor cannot determine a value for a required field, THEN THE System SHALL leave that field blank and mark it as requiring manual input by the Junior_Advocate.

---

### Requirement 8: Legal Issue Spotting

**User Story:** As a Junior_Advocate, I want the system to identify relevant IPC/BNS sections and flag procedural defects in uploaded documents, so that I can build a stronger case strategy.

#### Acceptance Criteria

1. WHEN extracted facts are available from an FIR or police report, THE Issue_Spotter SHALL cross-reference the document content against IPC and BNS section definitions and list all applicable sections.
2. WHEN a Panchnama or NDPS_Seizure_Memo is processed, THE Issue_Spotter SHALL check for the presence of independent witness signatures and flag the document if they are absent.
3. WHEN a procedural defect is identified, THE System SHALL attach a defect record to the Case_Record containing: defect type, source document name, and the specific clause or requirement that was violated.
4. THE Issue_Spotter SHALL complete its analysis within 30 seconds of receiving the extracted facts for a single document.

---

### Requirement 9: Explanation Layer (Tutorial Mode)

**User Story:** As a Junior_Advocate, I want contextual explanations for flagged procedural defects that cite Supreme Court precedents, so that I can learn the legal significance of each issue.

#### Acceptance Criteria

1. WHEN a procedural defect is flagged by the Issue_Spotter, THE Explanation_Layer SHALL generate a tooltip explanation of no more than 150 words describing why the defect matters legally.
2. THE Explanation_Layer SHALL include at least one Supreme Court or High Court precedent citation in each defect explanation.
3. THE System SHALL display defect explanations inline within the Review_UI adjacent to the flagged content.
4. WHERE a Junior_Advocate has disabled Tutorial Mode in their profile settings, THE System SHALL hide Explanation_Layer tooltips without affecting defect flagging.

---

### Requirement 10: Human-in-the-Loop Review Interface

**User Story:** As a Junior_Advocate, I want to review and correct AI-extracted content side-by-side with the original document, so that I can verify accuracy before the case file is finalized.

#### Acceptance Criteria

1. THE Review_UI SHALL display the original document (PDF rendered page or image) on the left panel and the AI-extracted text, timeline, and structured fields on the right panel simultaneously.
2. WHEN a Junior_Advocate edits a field in the right panel, THE System SHALL record the correction and mark the field as manually verified.
3. WHEN a Junior_Advocate clicks "Approve Structure", THE System SHALL finalize the Case_Record and navigate to the Case_Dashboard.
4. THE System SHALL prevent navigation to the Case_Dashboard until the Junior_Advocate has explicitly approved the structure via the Review_UI.
5. WHILE the Junior_Advocate is in the Review_UI, THE System SHALL auto-save all edits at intervals of no more than 30 seconds.

---

### Requirement 11: Automated Legal Research

**User Story:** As a Junior_Advocate, I want the system to automatically fetch relevant legal precedents based on the facts extracted from my uploaded documents, so that I can begin research without manual searching.

#### Acceptance Criteria

1. WHEN a Case_Record is approved via the Review_UI, THE Research_Engine SHALL automatically query for the top 5 most relevant legal precedents based on the extracted Applicable_Sections and Incident_Type.
2. THE Research_Engine SHALL return each precedent with: case name, citation, court, year, and a one-sentence relevance summary.
3. THE System SHALL display the fetched precedents in the Case_Dashboard within 60 seconds of case approval.
4. IF the Research_Engine returns fewer than 5 precedents, THEN THE System SHALL display the available results without error and indicate the total count found.

---

### Requirement 12: One-Click Draft Generation

**User Story:** As a Junior_Advocate, I want to generate a court-ready legal draft with a single click using the facts already extracted from my documents, so that I can save hours of manual drafting.

#### Acceptance Criteria

1. WHEN a Junior_Advocate selects a draft type (e.g., Section 439 Bail Application, Written Statement, Vakalatnama) and clicks "Generate Draft", THE Draft_Generator SHALL produce a complete draft document.
2. THE Draft_Generator SHALL auto-populate all date, name, jurisdiction, and section fields in the draft using values from the approved Case_Record.
3. THE Draft_Generator SHALL complete draft generation within 60 seconds of the request.
4. WHEN a draft is generated, THE System SHALL store the draft as a versioned document linked to the Case_Record.

---

### Requirement 13: Citation Verification and Hallucination Prevention

**User Story:** As a Junior_Advocate, I want all legal citations in generated drafts to be verified before I can submit them, so that I do not inadvertently rely on fabricated case references.

#### Acceptance Criteria

1. WHEN a draft is generated, THE Citation_Verifier SHALL check every legal citation in the draft against a verified citation database.
2. IF the Citation_Verifier identifies a citation that does not exist in the verified database, THEN THE System SHALL mark that citation as unverified and block the draft from being submitted for Chamber_Review.
3. THE System SHALL display all unverified citations to the Junior_Advocate with a clear warning before any submission action is available.
4. WHEN all citations in a draft are verified, THE System SHALL mark the draft as citation-verified and enable the Chamber_Review submission action.

---

### Requirement 14: Court-Specific Formatting

**User Story:** As a Junior_Advocate, I want generated drafts to be formatted according to the rules of the specific court identified in my documents, so that submissions are procedurally compliant.

#### Acceptance Criteria

1. WHEN a draft is generated, THE Formatter SHALL apply formatting rules corresponding to the jurisdiction extracted from the Case_Record (e.g., Rajasthan High Court, Supreme Court of India, Delhi District Court).
2. THE Formatter SHALL apply formatting rules covering: font, margin sizes, heading styles, cause title format, and page numbering convention for each supported jurisdiction.
3. THE System SHALL support formatting rules for a minimum of 5 distinct Indian courts or jurisdictions at launch.
4. IF the jurisdiction extracted from the Case_Record does not match any supported formatting profile, THEN THE Formatter SHALL apply a generic Indian court formatting template and notify the Junior_Advocate.

---

### Requirement 15: Role-Based Access and Chamber Review Workflow

**User Story:** As a Junior_Advocate, I want to submit my completed case file and draft for review by a Senior_Advocate, so that work is supervised before any court submission.

#### Acceptance Criteria

1. THE System SHALL enforce role-based access with two roles: Junior_Advocate and Senior_Advocate.
2. WHEN a Junior_Advocate submits a case file for Chamber_Review, THE System SHALL send a notification to the assigned Senior_Advocate.
3. WHILE a case file is pending Chamber_Review, THE System SHALL prevent the Junior_Advocate from modifying the approved Case_Record or any submitted drafts.
4. WHEN a Senior_Advocate approves a case file, THE System SHALL update the Case_Record status to "Approved" and notify the Junior_Advocate.
5. IF a Senior_Advocate rejects a case file, THEN THE System SHALL update the Case_Record status to "Returned" and deliver the Senior_Advocate's comments to the Junior_Advocate.
6. THE System SHALL maintain a complete audit log of all status transitions and approvals for each Case_Record.

---

### Requirement 16: Performance and Reliability

**User Story:** As a Junior_Advocate, I want the ingestion pipeline to handle large documents reliably, so that I can trust the system with complex multi-document cases.

#### Acceptance Criteria

1. THE System SHALL complete the full ingestion pipeline (upload → parse/OCR → classify → extract → issue-spot) for a single 500-page PDF within 5 minutes.
2. THE System SHALL process a batch of 20 simultaneously uploaded files without returning an error to the user.
3. IF any stage of the ingestion pipeline fails for a specific file, THEN THE System SHALL continue processing the remaining files in the batch and report the failure for the affected file only.
4. THE System SHALL support regional language content (Hindi and Gujarati) in OCR, classification, and fact extraction without degraded accuracy relative to English content.
