## 1. Executive summary

### 1.1 The thesis

The statement "in spite of tremendous hardwork the app is too far from enterprise grade launch" is half true, and the half that is false matters more.

**What is true:** the gap is not in engineering volume. This repository already contains a service worker, an edge API with idempotency and HMAC-signed webhooks, RLS migrations, a 15-chart adversarial accuracy corpus gated against an independent Swiss Ephemeris golden, structured logging with PII redaction, a written SOC 2 checklist, runbooks, a k6 load script, and six GitHub Actions workflows. That is well above the median for a solo-authored open-source project. You are not "too far" in the sense of missing features.

**What is also true, and is the actual problem:** enterprise buyers do not buy features. **They buy provable claims.** Every S1 in this review is the same failure mode wearing different clothes — _a claim that no artefact can prove, and in four cases a mechanism that is architecturally incapable of delivering the claim it is labelled with._

Concretely:

- `observability/alerts/alerts.yml` defines 7 alert rules with runbook links. **Nothing runs them.** There is no Prometheus, no Alertmanager, no Grafana instance, and no paging integration in the repo.
- `supabase/functions/metrics` serves Prometheus text from an **in-process counter registry inside a stateless serverless function.** Counters reset on every cold start and never aggregate across instances. The scrape semantics are wrong by construction.
- `src/api/v1` rate limiting is an **in-memory token bucket inside an edge function.** The effective limit is `configured_limit × live_instance_count`, and it resets on cold start. An API customer will exceed their tier and you will not know.
- `docs/ENTERPRISE_LAUNCH_GUIDE.md` asserts "Multi-Region Deployment" with an RTO < 15 minutes. There is no infrastructure-as-code in the repository, and no record of a failover having been executed.

A buyer's security reviewer reads a claim, looks for the artefact, and does not find it. That is where deals die — not at the feature list.

```

  |-- health, metrics, ingest-logs

Hosted on Netlify (static) + Cloudflare (asserted, not in repo)
```

### 2.2 The two structural facts that drive most findings

**Fact 1 — the product's brain runs in the browser.** The default configuration computes charts locally. `VITE_USE_SWISS_EPHEMERIS` and `VITE_USE_EDGE_EPHEMERIS` are build-time flags, and all `VITE_*` values are public by definition. Consequence: tier gating, feature flags, and calculation output are all client-trusted unless a specific edge path enforces them. Two engines (browser and edge) can disagree. See F-06, F-12, F-13.

**Fact 2 — the optional path is the enterprise path, and it is the less-tested path.** Demo mode requires no auth and no persistence, which is excellent for adoption and terrible for enterprise, because "no auth" means "no tenant, no audit, no isolation". See F-05, F-10, F-11.

## 4. Findings register

### S1 — Blockers

---

**F-01 — The observability stack is a specification, not a running system**

- **Severity:** S1
- **Evidence:** `observability/alerts/alerts.yml` (7 rules), `observability/alerts/uptime.yml` (5 monitors), `observability/dashboards/service-overview.json` (10 panels), `supabase/functions/metrics`, `src/observability/metricsRegistry.ts`. No Prometheus config, no Alertmanager receiver, no Grafana provisioning, no PagerDuty/Opsgenie/Slack webhook anywhere.
- **Why it matters:** you cannot claim an SLO you do not measure, and you cannot run an on-call rotation without a page. `docs/observability/runbooks.md` describes 6 incident runbooks "with STOP conditions" — but the trigger conditions are never evaluated, so the runbooks never fire.
- **Compounding defect:** `supabase/functions/metrics` returns Prometheus text from an in-process registry in a stateless function. Each instance has its own counters. A scraper sees a random instance's since-cold-start numbers. Latency histograms will be meaningless.
- **Acceptance criteria:** inject a synthetic failure (e.g. force `/health` to 503 for 6 minutes); a human's phone receives a page within 5 minutes; the incident is recorded in a channel; a Grafana panel shows the error-budget burn. Artefact: timestamped screenshot + alert JSON.
- **Fix sketch:** Grafana Cloud free tier + Prometheus remote-write, or Better Stack / UptimeRobot for the 5 synthetic monitors and Sentry Alerts for the error-rate and accuracy-degradation rules. Do not self-host Prometheus at this stage. Replace the in-memory metrics endpoint with a push-based counter (`client_logs`/`health_samples` already exist as tables) or accept Sentry-only until volume justifies it.
- **Effort:** 5–8 days.

---

**F-02 — Rate limiting is per-instance and therefore does not rate limit**

- **Severity:** S1
- **Evidence:** `src/api/v1/` token-bucket middleware; `supabase/migrations/20241007000007_public_api.sql` defines `api_keys`, `api_usage`, `idempotency_keys`, `webhook_endpoints`. The bucket itself lives in function memory.
- **Why it matters:** three compounding effects. (a) A tenant with a 10,000/day tier gets `10,000 × N` where N is live function instances. (b) A cold start resets the bucket to full, so a burst can be absorbed repeatedly. (c) Your `api_usage` metering will not match enforcement, so billing and quotas diverge silently.
- **Acceptance criteria:** 200 concurrent requests from one key against a 100/min limit; server returns 429 for requests 101+ in the window regardless of instance distribution. Test runs in CI. A second test proves the limit resets after the window, not after a cold start.
- **Fix sketch:** Postgres-backed sliding window using `api_usage` with an atomic `INSERT ... ON CONFLICT DO UPDATE ... RETURNING` in a `SECURITY DEFINER` function, called from the edge middleware. Upstash Redis is the alternative if latency matters more than consistency. Keep the in-memory bucket as a fast-path pre-check, never as the authority.
- **Effort:** 3–5 days.

**F-03 — No environment separation**

- **Severity:** S1
- **Evidence:** `netlify.toml` publishes `dist` with no branch/deploy-context conditional; a single `VITE_SUPABASE_URL` / `VITE_CLERK_PUBLISHABLE_KEY` per site; `supabase/migrations/` applied to one project; `.env.example` documents one set of variables.
- **Why it matters:** every Netlify deploy preview, every PR build, and every migration dry-run talks to the same Supabase project as production. A bad migration takes down prod. A destructive test writes into a real customer's data. `docs/runbooks/oncall.md` will have a page caused by a preview deploy.
- **Acceptance criteria:** three environments (dev / staging / prod) with distinct Supabase projects and Clerk instances; documented promotion path; `netlify.toml` `[context.branch-deploy]` and `[context.deploy-preview]` blocks pointing at staging; prod credentials never present in a preview build.
- **Fix sketch:** Netlify deploy contexts + a second Supabase project. Add `supabase/migrations` dry-run against staging in `deploy.yml` before the prod apply.
- **Effort:** 4–6 days.

**F-04 — Infrastructure is not code**

- **Severity:** S1
- **Evidence:** `netlify.toml` is the _only_ infrastructure artefact in the repo. Supabase project settings, Cloudflare DNS/WAF/load-balancing, Clerk configuration, Sentry project settings, PostHog, Flagsmith environment config, Netlify team-level extensions (the `NETLIFY_SKIP_EXTENSIONS` comment in `netlify.toml` is itself evidence that team-level dashboard state broke a deploy) — all dashboard-managed.
- **Why it matters:** three consequences. (a) You cannot answer "what changed?" during an incident. (b) You cannot rebuild from zero if a project is lost. (c) A buyer's reviewer asks "show me your network topology" and you have to screenshot a dashboard that may have drifted. The `NETLIFY_SKIP_EXTENSIONS = "true"` workaround is a live example: a team-level Neon extension was attached, broke builds, and was worked around in a committed file rather than removed — the comment even says permanent removal is a dashboard action nobody did.
- **Acceptance criteria:** `terraform plan` runs clean against production for DNS, WAF rules, redirects, and Supabase project config; a `terraform apply` from an empty state reproduces the environment; the Neon extension is actually removed and `NETLIFY_SKIP_EXTENSIONS` deleted.
- **Fix sketch:** Terraform with the Cloudflare and Supabase providers first (highest drift risk). Clerk/Sentry/PostHog/Flagsmith config can be captured as documented declarative JSON exports in `ops/` rather than full providers — pragmatic, and enough for an auditor.
- **Effort:** 8–12 days. Start with Cloudflare + DNS only; it is the cheapest credibility win.

### S2 — Critical

**F-05 — No SSO, no SCIM, no enforced MFA, no admin audit trail**

- **Severity:** S2
- **Evidence:** `@clerk/react` and `@clerk/themes` present; `src/auth/`; `docs/SOC2_PREPARATION_CHECKLIST.md` marks "Privileged access monitoring", "MFA for admin accounts" and "Access removal on offboarding" as in-progress; `src/components/MfaSetup` referenced. No SAML connection artefact, no SCIM endpoint, no admin action log.
- **Why it matters:** SSO is the single most common hard gate in enterprise procurement. A 500-person buyer will not issue individual accounts. "Access removal on offboarding" is an audit finding if unproven.
- **Acceptance criteria:** Clerk SAML connection working against at least one IdP (Okta or Entra ID dev tenant); SCIM endpoint receiving create/deactivate events; MFA enforced by policy for any org admin role; every privileged action (key create/revoke, role change, data export) written to an append-only `admin_audit` table with actor, action, target, timestamp, correlation ID.
- **Fix sketch:** Clerk's SAML/SCIM is a paid-plan feature — confirm your plan tier covers it before quoting it to a buyer. The audit table is 2 days of work and unlocks three separate checklist items.
- **Effort:** 6–10 days.

**F-06 — Authorization is client-trusted in the primary product surface**

- **Severity:** S2
- **Evidence:** engine, tier config, `useFeature`/`useTierLimits`, and `FeatureGate` all execute in the browser; Flagsmith evaluates client-side; `src/config/flags/schema.ts`; `VITE_*` are public. Only `src/api/v1` enforces scopes server-side.
- **Why it matters:** the web app is where users spend their time, and in the web app the "paywall" is a React conditional. Anyone with devtools can unlock preview modules. That is fine — until an enterprise buyer asks "is the tier enforced?" and the honest answer is "in the API, yes; in the app, cosmetically."
- **Acceptance criteria:** a written `docs/trust/AUTHORIZATION_MATRIX.md` listing every gated capability, its client-side check, and its server-side enforcement point — with an explicit "not server-enforced (accepted)" column for the ones that are cosmetic. For every _billable_ capability, a server-side check exists.
- **Fix sketch:** route all billable capability through edge functions; keep Flagsmith client-side for UI-only flags. Document the boundary rather than trying to eliminate it.
- **Effort:** 5–8 days.

**F-07 — Documentation drift and claim inflation**

- **Severity:** S2 (cheap to fix, disproportionately damaging)
- **Evidence — four concrete contradictions:**
  1. `package.json` says `"version": "0.1.0"`. The launch guide's T-Zero check asserts `{"status":"healthy","version":"1.0.0"}`.
  2. Test count appears as **1476** (README badge), **1316** (`docs/ENTERPRISE_LAUNCH_GUIDE.md` launch-day check), and **291** (the `test:core` commit message in `PRODUCT_BRIEF.md` history).
  3. Accuracy corpus is **15 charts** (`tools/accuracy/corpus/charts.jsonl`, README, METHODOLOGY.md) but `docs/SOC2_PREPARATION_CHECKLIST.md` claims **155/155 charts**, and a commit message repeats 155/155.
  4. README says "4 core features production-ready" while the same README documents auth and persistence as optional and 12+ modules as preview.
- **Why it matters:** a reviewer who finds one inflated number starts doubting all of them. This is the cheapest credibility purchase available to you.
- **Acceptance criteria:** a `npm run docs:verify` script that parses the real values (test count from vitest JSON reporter, corpus size from the JSONL line count, version from `package.json`) and fails CI if any doc contains a stale figure. Single `VERSION` source feeding `package.json`, the health endpoint, and every doc.
- **Fix sketch:** half a day for the script, one day to reconcile the docs. Do this first — it is the highest ratio of trust gained to effort spent in this entire register.
- **Effort:** 1.5 days.

**F-08 — No SAST, no DAST, no secret scanning, no penetration test**

- **Severity:** S2
- **Evidence:** `.github/workflows/security.yml` performs `npm audit` (blocking at moderate for prod, non-blocking for full tree). `.github/workflows/dependency-gate.yml` splits prod/dev audits. That is the entirety of application security automation.
- **Why it matters:** dependency audit catches CVEs in packages. It does not catch a missing authorization check, an injection in your own Hono handlers, a leaked service-role key in a fixture, or a misconfigured RLS policy. Your own `docs/SOC2_PREPARATION_CHECKLIST.md` lists OWASP Top 10 via Burp and OWASP ZAP as unticked, and the pen test as unticked.
- **Acceptance criteria:** (a) CodeQL or Semgrep in CI, blocking on `high`; (b) `gitleaks` on every PR; (c) OWASP ZAP baseline scan against a staging deploy in `deploy.yml`; (d) one external penetration test with a report PDF filed in `docs/launch/security-review.md` (which already exists as a stub) and all High findings remediated.
- **Fix sketch:** (a)–(c) are each under a day and can be done this week. (d) is the schedule item — budget 2–3 weeks lead time and roughly $3k–$8k for a scoped web + API test. Free alternatives: a well-run self-assessment plus a bug-bounty-style public call is acceptable for G2, not for G3.
- **Effort:** 3 days (a–c) + external lead time.

**F-09 — Accessibility is unproven**

- **Severity:** S2 for public-sector and large-enterprise; S3 otherwise
- **Evidence:** `npm run test:a11y` runs one file (`src/tests/week5/accessibilityGaps.test.tsx`). `eslint-plugin-jsx-a11y` is configured. Radix primitives give a strong baseline. No `axe-core` dependency, no axe assertions in Playwright, no conformance report.
- **Why it matters:** India's public-sector and BFSI buyers ask for WCAG conformance; EU buyers ask for EN 301 549. "We use Radix" is not an answer. Also: your stated audience includes diaspora users and beginners — the same people most harmed by poor a11y.
- **Acceptance criteria:** `@axe-core/playwright` running against every route in `tests/e2e/all-routes`, failing on `critical` + `serious`; keyboard-only traversal test for the four core flows; a published `docs/trust/ACCESSIBILITY_CONFORMANCE.md` (ACR) with WCAG 2.2 AA criteria, status, and known exceptions.
- **Fix sketch:** the automated half is 2–3 days. The ACR is a day of writing. Full manual audit (screen reader passes) can follow at G3.
- **Effort:** 3–4 days.

**F-10 — Multi-tenant isolation is asserted, not proven**

- **Severity:** S2
- **Evidence:** `supabase/migrations/` contains owner-scoped RLS policies; the `feat(api)` commit references "RBAC types, org/role migrations, RLS policies". There is no test that org A cannot read org B.
- **Why it matters:** this is _the_ question for a multi-tenant SaaS. Worse, edge functions using the service-role key **bypass RLS entirely** — so isolation depends on every handler remembering to filter, which is exactly the class of bug that tests exist to catch.
- **Acceptance criteria:** a test suite that seeds 3 orgs × 5 users × 20 resources, then asserts, for every table and every role: correct reads succeed, cross-tenant reads return empty, cross-tenant writes are rejected. Runs in CI on every migration. Plus an explicit inventory of which edge functions use service-role and what they filter on.
- **Fix sketch:** this is a `pgTAP`-style suite or a Vitest integration suite hitting a staging Supabase with seeded JWTs. Either is fine; the artefact matters more than the tool.
- **Effort:** 4–6 days.

**F-11 — PII governance is incomplete**

- **Severity:** S2
- **Evidence:** birth data (name, date, time, place) is the core PII and is quasi-identifying. Export and delete exist and are `VERIFIED`. Missing: field-level encryption for the most sensitive columns; a retention policy with enforcement beyond the `client_logs` prune function; a DPIA; cookie/consent UI; a published sub-processor register; any data-residency statement.
- **Why it matters:** India's DPDP Act and GDPR both require consent capture, a lawful-basis record, retention limits, and a sub-processor list. Your SOC2 checklist already has `docs/policies/DATA_CLASSIFICATION.md` and `ACCEPTABLE_USE.md` marked in-progress, and lists DPAs as "signed" for six vendors with no artefact in the repo.
- **Acceptance criteria:** (a) `docs/trust/SUBPROCESSORS.md` listing Supabase, Clerk, Netlify, Cloudflare, Sentry, PostHog, Flagsmith, Logtail with purpose, region, and DPA status; (b) `docs/trust/RETENTION.md` with a per-table retention period and the cron that enforces it; (c) working consent capture with an audit row; (d) a data-residency statement — Supabase region is the single most important line in your trust pack, so choose it deliberately and say so.
- **Fix sketch:** the documents are 2 days. The consent UI is 2 days. Retention cron is 1 day. Field-level encryption of `birth_time`/`birth_place` can be deferred if you document the decision.
- **Effort:** 5–7 days.

### S3 — Major

---

**F-12 — Two calculation engines means two answers**

- **Severity:** S3 (S2 the moment you have an API customer)
- **Evidence:** browser engine by default (`VITE_USE_SWISS_EPHEMERIS=false`); `supabase/functions/calculate-kundli` is a second implementation path; `VITE_USE_EDGE_EPHEMERIS` is documented in `.env.example`.
- **Why it matters:** a customer who uses both the web app and the API will eventually get different numbers for the same birth data. In Jyotish, one degree changes a nakshatra and therefore the reading. Divergence is a support ticket that costs you the customer's confidence permanently.
- **Acceptance criteria:** a single canonical engine; a conformance test asserting browser and edge paths produce identical output for all 15 corpus charts at full precision; the active engine named in every payload.
- **Effort:** 4–6 days.

---

**F-13 — Accuracy output is not versioned**

- **Severity:** S3
- **Evidence:** `src/generated/summary.json` is regenerated at build; `scripts/publish-accuracy.mjs`; `netlify.toml` publishes before build. No engine version is embedded in chart payloads or PDFs.
- **Why it matters:** change the engine and every previously-issued chart changes silently. A practising astrologer who reprints a client's chart and gets a different D9 will not trust you again. Enterprises need "the report issued on date X is reproducible".
- **Acceptance criteria:** every chart response and every PDF carries `engine_version`, `ayanamsa`, `ephemeris_model`, `delta_t_model`, `corpus_version`; an `ENGINE_CHANGELOG.md` records every accuracy-affecting release; the SDK and OpenAPI spec expose these fields.
- **Effort:** 3–4 days.

---

**F-14 — Reports are client-rendered and non-archival**

- **Severity:** S3
- **Evidence:** jsPDF 4 + jspdf-autotable 5 in the browser; `docs/WEEK9_PDF_REPORT_SPEC.md`; Ganesh-motif templates.
- **Why it matters:** no server-side render means no deterministic artefact, no hash, no template version, and no way to re-issue a byte-identical report. Enterprise legal/HR use cases (wedding matchmaking at scale, bulk employee panchang) want archival output.
- **Acceptance criteria:** an edge-function render path producing a versioned PDF with a SHA-256 in the footer and template version in metadata; a test that the same input yields the same hash.
- **Effort:** 5–7 days.

---

**F-15 — CI is thin relative to the claims, and main is unprotected**

- **Severity:** S3
- **Evidence:** `ci.yml` runs lint + typecheck + `test:run` + build on one Node version, on push/PR to `main` only. Not gated: Playwright E2E (`test:e2e` exists), Lighthouse budgets (`test:perf` exists but is not in CI), the accuracy corpus (separate `accuracy.yml` — good), coverage thresholds, migration dry-run, bundle-size. No `CODEOWNERS`. No evidence of branch protection or required reviews.
- **Why it matters:** `docs/QUALITY_GATE.md` and `CONTRIBUTING.md` describe a gate that CI does not enforce. Required status checks on `main` are a change-management control your own SOC 2 checklist needs.
- **Acceptance criteria:** E2E, axe, perf budget, and a coverage floor are required checks on `main`; branch protection on with required review and linear history; `CODEOWNERS` for `supabase/migrations/` and `src/lib/vedic/`; the accuracy workflow is a required check.
- **Effort:** 3–4 days.

**F-16 — Service worker can serve a stale app against a new API**

- **Severity:** S3
- **Evidence:** workbox precaching/routing/strategies; `vite-plugin-pwa`; `netlify.toml` correctly sets `must-revalidate` on `/service-worker.js` and HTML. The app shell itself is precached.
- **Why it matters:** offline capability is a genuine differentiator (diaspora users, spotty networks). But a precached shell plus a changed API contract equals mysterious client-side failures that never reproduce for you. Netlify correctly never caches the SW file — good — but the update strategy (`skipWaiting`, `clientsClaim`, prompt-vs-force) is undocumented.
- **Acceptance criteria:** documented SW versioning and update policy; a test that a new deploy is picked up within one navigation; a documented decision on forced update vs prompt; the decision recorded in `docs/`.
- **Effort:** 2–3 days.

---

**F-17 — No support model**

- **Severity:** S3
- **Evidence:** `ops/status/` exists; `ops/warroom/` exists; `docs/runbooks/oncall.md` exists. No ticket intake, no support email, no published severity→response-time table, no live status page, no on-call rotation, no paging.
- **Why it matters:** "Who do I call at 03:00?" is asked in every enterprise deal. Your launch guide has a War Room role table for launch _day_ and nothing for month 3.
- **Acceptance criteria:** published support tiers with response/restore targets per severity; a ticket intake channel; a live status page; an on-call rotation with escalation; runbooks linked from each alert.
- **Effort:** 3–4 days.

**F-18 — Commercial and legal artefacts are absent**

- **Severity:** S3
- **Evidence:** `docs/SOC2_PREPARATION_CHECKLIST.md` lists six vendors as "DPA signed, SOC 2 Type II" — with no copies in the repo. SLA percentages exist as a YAML block with no measurement mechanism. Auditor quotes ($20k–$60k) are researched. `docs/API_MONETIZATION_STRATEGY.md` exists.
- **Why it matters:** these are the documents that get a deal to signature. They are cheap to produce and are currently the longest lead-time item after the pen test.
- **Acceptance criteria:** a `docs/trust/` pack containing DPA (template), sub-processor register, SLA with credit schedule, security whitepaper (2–4 pages), and a pre-answered CAIQ-lite / SIG-lite answer bank. Vendor DPAs actually filed.
- **Effort:** 4–5 days (mostly writing; have a lawyer review the DPA and SLA).

**F-19 — Backup and DR are scripted but never executed**

- **Severity:** S3
- **Evidence:** `ops/backups/backup.sh`, `ops/backups/restore.sh`, `.github/workflows/backup.yml`, `ops/deploy/rollback.md`, `ops/deploy/canary.md`, `docs/runbooks/restore-drill.md`. The launch guide asserts RTO < 15 minutes. The SOC 2 checklist lists the restore drill, failover test, and DR drill as untested with future quarters attached.
- **Why it matters:** an unexecuted backup is a hypothesis. RTO and RPO are currently marketing numbers.
- **Acceptance criteria:** executed restore into a scratch project with measured wall-clock time; measured RPO from the last backup; point-in-time-recovery verified; a documented failover test; all three written up with timestamps as evidence.
- **Effort:** 3–4 days.

## 9. What is genuinely strong — do not lose this

Reviewers spend all their time on gaps, so it is worth naming what is above the bar, because these are your differentiators and your marketing:

1. **The historical timezone resolver.** `src/lib/birthTimezone.ts` handling the 1941–42 and 1942–45 wartime offsets, with a CI wiring guard (`chartTimezoneWiring.test.ts`) that fails if any production code bypasses the wrapper. Most Jyotish apps hardcode IST and are simply wrong for pre-1947 births. The 16.49° ascendant delta you measured is a full rashi. This is a real, defensible, verifiable claim, and it is the single best thing in the repository.
2. **An adversarial accuracy corpus gated against an independent authority.** Regenerating the golden from `swisseph-wasm` rather than from the engine under test is a genuinely sophisticated decision — it removes the tautology. Most projects never notice that their golden data is self-consistent rather than correct.
3. **Published methodology with an explicit "what is not verified" list.** `docs/accuracy/METHODOLOGY.md` and the `/accuracy` page naming Yogas, Shadbala, Ashtakavarga and Varga as ungated is intellectual honesty that buys trust.
4. **The `netlify.toml` header set.** HSTS with preload, a real CSP with named sources, Permissions-Policy with `interest-cohort` disabled. Better than most funded startups.
5. **Verifiable right-to-erasure and right-to-portability.** Rare at this stage.
6. **Commit discipline.** Conventional commits, commitlint, husky, a commit history that explains _why_. This is the thing that makes the F-07 fix cheap.
